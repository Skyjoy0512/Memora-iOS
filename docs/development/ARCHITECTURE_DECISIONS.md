# 公開準備の設計判断

- **資格情報の更新を原子的に扱う。** 同じ Security の更新でデータと端末限定の保護属性を適用する。ロック中に以前の値を返すメモリキャッシュを廃止する。端末のセキュリティ設定と OS の判断に従う。[Apple の Keychain 更新](https://developer.apple.com/documentation/security/updating-and-deleting-keychain-items)・[アクセス属性](https://developer.apple.com/documentation/security/ksecattraccessible)
- **ChatGPT アカウント連携は開発ビルドでのみ明示有効化する。** 現行コードには専用の Responses 推論経路がなく、公開形態での適格性も未確認。公開版の案内は既存 BYOK に揃え、過去に保存した連携を利用者が解除できるようにする。[公式の適用範囲](https://developers.openai.com/siwc/token-sharing-open-source)・[公式の推論経路](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference)
- **SQLite の現行原本を維持し、移行の判断は計測に基づく。** バッファの寿命を SQLite の同期実行範囲に限定して一時コピーを減らす。件数・ID・メディアを保証できる移行が確立するまで、既存データに破壊的な移行をかけない。
- **OCR と検索は既存原本から再構築可能にする。** 画像本文は参考情報として扱う。画像への参照と取得時点の有効性、ローカル閲覧・クラウド送信の権限を検索経路に引き継ぐ。
- **会議の参加方式は停止と権限の境界を先に決める。** 調査と段階的な実装条件は [オンライン会議 Bot](../ONLINE_MEETING_BOT.md)。
- **クラウドで履歴を再利用するには、元のクラウド実行の来歴が必要。** 新しいクラウドエージェントがリクエスト境界で採取した来歴だけを識別し、ワークスペース、記憶、出典の版、現在の許可を再確認する。旧回答や端末内の回答は表示でき、端末内での既存の検索条件も維持する。

## 記録単位の保存に向けた移行条件

`StorageKey.meetings` は個別の編集だけでなく、録音復旧、音声・動画の取り込み、要約とタスクの確定、写真の削除と取り消し、プロジェクト移動、人物の統合、ゴミ箱、バックアップ復元から使われる。同期・非同期の両方があり、複数の保存キーをまとめて確定する操作もある。起動時の読込と、同期確認用の読込は別の入口を通る。

1. `RecordStore` と同じ SQLite 内に、記録 ID・表示順・バージョン・記録の payload を保持する表を検討する。最初は `Meeting` の既存 codec を使い、文字起こしや写真を別形式に置き換える変更を同時に入れない。
2. 各機能が記録変更を区別して渡す共通の書込契約を作る。記録・タスク・原本参照・ドラフトの変更は、今と同じ SQLite トランザクションで成否が揃うことを受け入れ条件にする。同期書込と待ち行列も同じ順序で確定し、失敗中の UI は未保存状態を維持する。
3. 既存 BLOB を原本として保持したまま、一時世代に小分けに取り込む。開始時の原本指紋を記録し、再開時に違っていれば作成中の世代だけを破棄して作り直す。件数、IDの一意性、表示順、記録の再デコード、添付参照が一致した時だけ原本ポインタとスキーマ版を一緒に更新する。
4. 切替の後に古い BLOB を現行データとして読ませると編集が失われる。現行表から作る手動バックアップと復旧経路を検証し、旧版で扱う場合の再エクスポート条件を明記する。既存 BLOB を退避した状態で検証を始め、実利用データに切替を適用する前に許可されたテスト環境を使う。

受け入れ条件は100〜5万件の件数／順序／ID／元音声の一致、途中終了・書込失敗・競合からの再開、復元と取り消しの原子性、1件の変更時に全件を encode しないこと。起動と SQLite の書込みには別の計測を入れる。現在は保存箇所の調査と既存形式の保護まで実施。新しいスキーマへの切替は未実施。
