# 編集・外部送信の状態変更への対応 — 2026-11-10

## 個人データの編集制限

タスクの完了・日付・削除・挿入・復元、資料の追加・更新・削除、プロジェクトの
追加・名前変更・削除・ファイル移動、音声の削除、会議／日記のゴミ箱操作・期限整理、
Undoに、復元中・チーム選択中・保存保護中の拒否を追加した。
自動位置記録の受信箱も、その間は取り込まず保持する。

検証: `run-person-task-checks.sh`、`run-artifact-provenance-checks.sh`、
`run-recording-media-checks.py`成功。本番メソッドと実SQLiteを使い、各状態で
メモリと保存済みのバイトが変わらず、写真・音声が削除されないこと、Undoが
消費されないこと、個人モードへ戻ると編集できることを検査した。
プロジェクトの関連資料／チャットと通知・検索サービスはfixture。
`bitrig preview -platform iOS`成功（既存警告11件）。実機・全E2Eは未検証。

## Webhookの依頼と通信

- 各依頼に送り先・URL・ワークスペース世代・会議／タスクのスナップショットを保持し、
  送信開始直前と応答後に現状と照合する。モデルの索引・関連タスクのキャッシュを
  無効化した後に検査し、古い索引で許可を確認しない。
- 無効化・削除・URL変更・元データ／許可変更・ワークスペース変更・復元・保存保護で、
  不一致の待機中／通信中タスクを同期的にキャンセルする。OFF→ONでも復活しない。
- 完了通知は依頼IDを照合し、古い依頼が新しい送信結果を上書きしない。
  テスト送信は既存の用意したテスト文のみを使う。
- 専用のephemeralセッションを使用し、Cookie・保存資格情報・キャッシュを使わない。
  リダイレクトを拒否し、送信512KiB・応答64KiBを上限とする。

検証: `run-webhook-lifecycle-checks.py`成功。本番のモデルメソッドとHTTP送信処理を
使用し、待機中／送信中の20条件、OFF→ON、古い応答、テスト文の分離を検査。
HTTPはURLProtocolで、許可拒否時の未送信、HTTPS、サイズ制限、キャンセルを検査する。
リダイレクトはdelegateの拒否と302の失敗を検査。実サーバーは使っていない。
モデル・キーチェーン・ネットワーク境界はfixtureで、実サービスの受信は未検証。
すでに通信へ渡ったデータを受信側から取り消す保証はない。変更を検知して以降の
処理を止め、古い送信を成功として表示しないことを対象とする。

## CloudKitの共有準備

- 準備ごとにID、ワークスペース世代、対象会議・タスク・プロジェクト、共有者名を
  保持する。利用可否の確認後と、ゾーン・共有レコードの保存・購読設定の前後に、
  元データ・共有許可・チームプラン・復元／保存保護状態を再検証する。
- 状態変更時には準備IDを失効させ、実行Taskもキャンセルする。OFF→ONで復活せず、
  古い利用可否確認が後の共有を置き換えることも防ぐ。
- 保存が失敗した場合や、保存中に許可が失効した場合は、この準備だけが作成した
  root recordとCKShareの削除を試みる。削除処理は準備Taskのキャンセルを引き継がず、
  既に存在しないIDは削除済みとして扱う。削除失敗は隠さず表示する。
- サービスから戻った後にも再確認し、有効な場合だけシステムの共有画面へ渡す。
  現時点で呼び出しのない共有更新APIも、利用側の検証を必須引数にした。

検証: `run-cloud-share-lifecycle-checks.py`成功。本番のモデル・共有作成・削除メソッドと
実際のCKRecord／CKShareを使用。利用可否・ゾーン・保存・購読で待機させた36条件、
古い確認結果、削除の再試行、削除失敗の表示を検査した。モデル・利用可否・
データベースはfixtureで、iCloudへの通信や実コンテナの変更は行っていない。
共有設定・schema・entitlementsは変更していない。

既に送信開始したデータを遡って未送信にする保証はない。新規共有では共有画面を
出さず、一時データの削除を試みる。ローカルの許可変更を、既に招待・受信された
共有スナップショットへ自動で反映する機能は、この修正の対象に含めない。
一時データの削除失敗は表示するが、そのIDをアプリ再起動後まで保持して自動再試行する
台帳は未実装。実iCloudでの取消し・削除・再接続の検証も残る。
