# カスタム要約の入力分割と条件の保全

2026-10-24。前回の [端末内要約の階層](ON_DEVICE_RELATIONS.md) に続く内部修正。UI・テンプレートの最終出力スキーマ・SQLite形式は変更しない。

## 修正

以前の `OnDeviceSummarizer.templateDocument` は、中間ノートを1行ずつ文字数で分けていた。親の箇条書きが先の入力に、理由・条件の行が次の入力に分かれる可能性があった。また改行の1文字を上限計算に含めず、単独の長い項目は上限を超えてもそのまま渡していた。

`SummaryRelationMarkdown.groups` で、既存と同じ描画行を親＋根拠の一組として再利用する。新しい `SummaryTemplateNotes.prepare` は組を切らず、改行とMarkdownエスケープ後の実際の文字数で分割する。順序・文面・要点と決定の区別・関係の重複除去を維持する。

カスタム／マーケット用の自由形式・見出し指定形式の両方が、この共通の準備処理を通る。1組でも上限を超えれば、本文用の追加生成セッションを作る前に全話題の準備を失敗させ、既存の `contextTooLarge` を返す。条件・否定の省略、前半だけの完成扱い、サンプルによる穴埋め、別エンジンへの無断送信はしない。文字起こしからの話題抽出と概要生成はこの準備より前に行われるため、それらのモデル実行を防ぐ変更ではない。

新しい生成段階や外部通信は追加しない。ただし、親と根拠を一体で配置すると入力の区切り方と個数が変わり得る。呼出回数・生成速度・メモリが必ず改善するとは主張しない。文字数上限は作業メモ部分だけの予算であり、指示・タイトル・利用者プロンプトを含む実際のトークン上限を証明するものでもない。

## 検査と未検証の境界

- `SummaryTemplateNotesChecks` を既存の `run-summary-reading-checks.sh` と、その呼出元のホスト回帰へ接続。親と条件が分かれる文字数境界、複数の根拠、末尾の否定、要点／決定の親の種類、重複、改行込みのぴったり上限、長すぎる後続話題、空入力、複数行、結合文字／家族絵文字、エスケープで増える文字数を本番コードで確認する。
- 従来の根拠付き階層、4組み込み形式、読み戻し・編集・SQLite再保存も引き続き回帰対象。関係なしの中間ノートは従来と同じ文面・順序になることを照合する。
- E2Eは既存の `summary-relations` と `summary-sample` を利用し、既存の読み取りUIに対する影響を確認する。実モデルにカスタム要約を生成させるテストではない。専用Simulatorの検証用データのみを扱い、利用者のプレビューのDBは置き換えない。
- 実モデルによる自由形式／見出し指定形式の最終本文で、因果・否定・条件が保持されるかは未検証。入力分割の修正だけで、モデル出力の意味や階層を保証するものではない。実機の速度・メモリ・電池のBefore/Afterは未計測。

## 残課題

- P0：実音声と対応実機で、カスタム形式の最終出力、長時間会議、否定／提案／却下の意味保全を評価する。

- P2：カスタムの最終生成スキーマで階層を型として保持するかは、既存テンプレート互換と実測の上で判断する。今回は変更していない。
