# Ask AIの下書きの読み込み・退避・復旧

## 変更

- 本文・メンション・添付参照の形式破損と、保存先そのものの読み取り失敗を分けた。
  形式破損だけならAsk AIの入力を保護し、記録全体を保存停止にはしない。
  SQLiteの読み取り失敗や記録本体の保存保護は従来どおり維持し、復旧操作では解除しない。
- メンション／添付参照のJSONも検証する。読めないJSONを空欄として保存し直さない。
- 入力欄の案内と「設定 → データ管理 → Ask AIの下書き」から、明示的に復旧できる。
  復旧までは本文・メンション・添付参照の自動保存を止め、空の入力欄で上書きしない。
- 元の3フィールドを正確なバイト列のままSQLiteの別文書へ退避し、退避一覧への追加と
  読める本文・メンション・添付参照の復旧を1つのトランザクションで保存する。
  待機中の最新入力も参照し、途中で失敗すれば全変更を取り消す。
- 退避データはUUID別に保持し、古い退避を置き換えない。健康な下書きへの重複操作では
  新しい退避を作らない。一覧が読めない場合も空の一覧で置き換えない。
- 退避データはシステムのファイル書き出しからJSONで取り出せる。本文と添付参照の
  元データを含むが、添付ファイル本体は含まない。Memoraの通常のバックアップ書き出しの
  対象には追加していない。チーム選択中・復元中は操作を制限する。

## 検証

`run-composer-recovery-checks.py`は本番のComposerDraftStore／DraftStore／RecordStoreと
LocalStoreのSQL・ロック・トランザクションを実行する。LocalStoreのsingletonと添付解決先だけを
一時ディレクトリに差し替えるため、実行中のアプリやホストのデータへは触れない。

- 新旧形式の本文、本文／メンション／添付参照の破損、JSON破損、元バイト列の完全一致。
- 退避保存・一覧保存・本文保存・メンション保存・添付参照保存・添付参照削除の6段階で、
  SQLiteトリガーにより失敗させる。全行が失敗前のままであることと、再試行成功を検証。
- 退避一覧の破損時の拒否、過去の退避保持、保存待ちの最新本文、別接続からの再読み込み。
- チーム／記録の保存保護／復元／回答中の拒否。無関係な記録を変えないこと。
- テーブルを読めない実SQLiteエラーを、下書きの形式破損と区別すること。

既存のRecordStoreFailureChecksはSwift 6で成功。コンポーザーの送信・レイアウト・
UI操作の関連検査も成功。送信fixtureに不足していたprocessingStatusを現行の型へ合わせた。
両アーキテクチャのiOSプレビュー更新は成功し、新しい警告は増えていない。
内蔵iPhoneで設定から新画面へ遷移し、通常状態と空の退避一覧の表示を確認した。
アクセシビリティの最大文字サイズでも末尾までスクロールして読めることを確認し、
確認後は文字サイズを通常へ戻した。

実データを破損させるシミュレータ操作は行っていない。破損状態の画面から実際に復旧する
E2E、システムのファイル保存先選択、VoiceOverの読み上げ、実機は未検証。

## 残件

- CloudKitの一時データ削除失敗を、再起動後に再試行する仕組み。
