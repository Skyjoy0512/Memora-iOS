# プロジェクト検索の評価 — 2026-10-15

## 対象と再実行

`ProjectSearchIndex`のSQLite FTS5検索から`ProjectContextBuilder`が実際に
送信候補にする抜粋までを測る。LLMの回答品質の評価ではない。
コーパスは`tools/checks/fixtures/project-search-quality.json`。全件合成データで、
実ユーザーの資料、外部アカウント、API keyを使わない。

```sh
python3 tools/checks/run-project-search-quality.py
python3 tools/checks/run-project-search-quality.py --baseline-ref b75b841
bash tools/checks/run-next-generation-checks.sh
```

一時ディレクトリを指定する場合は`MEMORA_CHECK_ROOT`を設定する。
単独runnerは一時SQLite/実行ファイルを終了時に削除する。baselineはそのGit版の
rankingの2ファイルだけを読み、現在の同じコーパス/driverで測定する。
品質の合否判定を外して以前の値を報告し、アプリの保存領域は触らない。
実行環境はApple Silicon Macのhost Swift Debug、SQLite FTS5。

## 固定した正解

13資料のうちalphaプロジェクトの参照可11件を検索へ渡す。
参照取消済み1件を除き、betaの1件を別projectで先に索引化して混入を検査する。
2026-10-15を基準日とする12問（回答可能11問、該当なし1問）で、日付、
未決事項、担当/期限、予算、音声の送信方針、活動件数、出張を扱う。
複数資料を正解とする2問と、日本語の言い換えを含む。

長いPDFのケースは、18ページ目を表す合成テキストの末尾に正解を置き、
実際の700文字の抜粋に条項とページ番号が残ることを検査する。
**PDFファイルの実解析やレイアウト評価ではない。**
画像/OCRの誤りや、本物の文書の多様性もこのコーパスでは評価しない。

## 測定結果

同じfixtureを変更前`b75b841`と今回のrankingへ適用した結果。
質問ごとに送信抜粋から資料IDを重複除去し、その順を評価する。

| 指標 | 変更前 | 変更後 |
| --- | --- | --- |
| 正解が先頭の質問数（回答可能11問） | 9/11 | 11/11 |
| 正解資料のRecall@3（質問ごとの平均） | 0.864 | 1.000 |
| 最初の正解の逆順位の平均（送信資料列） | 0.848 | 1.000 |
| 送信資料中の非正解率（質問/資料IDの組） | 0.755 | 0.500 |
| 該当なしで資料を送らなかった質問 | 0/1 | 1/1 |

変更前は「9月と10月の計画予算」で活動記録が先頭に来て、上位3件から旧予算が
落ちた。「納期と担当」では期限が書かれた会議が上位3件に入らなかった。
今回は両方の正解が上位へ移った。一方、担当/音声方針/録音件数などでは
無関係な予算や会議も送られており、混入は解消していない。
全12問のID/正解/上位3件/送信件数は実行時に出力する。

品質ゲートは、この固定セットで全回答可能問の先頭一致、Recall@3=1、
該当なしの送信ゼロ、非正解率<=0.5。開発に使用した小さなセットの回帰防止であり、
未知の質問への正解率や統計的な改善率を示すものではない。

最終統合実行のhost所要時間はp50 0.55ms、p95 13.52ms（12回、最初の索引化込み）。
コンパイル/buildとの並行実行を含み、1実行の参考値に留める。
端末内の時間、メモリピーク、起動、実機Releaseの改善率は未測定。

## 実装した小さな調整

- 保存済み索引の2-gram形式とSQLite schemaは変更しない。queryのみ、
  他の語を伴う場合に助詞などのひらがなだけのgramを除く。
  ひらがなだけの名前は元のgramで検索する。
- 期限/納期/締切、予算/費用/見積/支出、公開/リリース、未決/保留、録音/収録の
  小さなローカル語彙をqueryへ追加する。意味検索モデルではなく限定的な語彙拡張。
- 本文をタイトルより重視し、同じgramの出現は2回まで数える。
  同じ言葉の繰返しだけで重みが増え続けないようにする。
- 最上位の40%以上のscoreに絞る。タイトルだけで一致する資料も残し、
  一致がない普通の質問に直近資料を機械的に送らない。
  明確な日英の短縮/続行/要約等の依頼は、従来の会話用fallbackを保つ。
  「このプロジェクトの進捗をまとめて」など対象全体を求める依頼も、許可された
  プロジェクト内のboundedな資料から始める。網羅的に全件を読む保証ではない。
  既存のread toolが検索済みIDを指定した場合も、現在許可された対象だけに絞って
  不一致時の本文読み取りを保つ。指定IDそのものをアクセス許可として扱わない。
- 既存の8抜粋/資料ごと2抜粋/文字数/200候補/32 query gramの上限は維持。
  同点の順序は元の候補順で固定。LLMや外部embeddingは呼ばない。

## 権限と追加検証

driverは現在参照可の入力snapshotを組み立て、indexとcontext双方のproject/allowed
境界を確認する。資料の本文更新、削除、参照取消を反映すると古い証拠が返らない。
`ProjectContextChecks`では送信量/資料数/引用番号、他project/非公開除外、
ひらがな/タイトルのみ/ローカル言い換え/該当なし/日英follow-upも検査する。
`ProjectSearchIndexChecks`は実SQLiteの再起動・更新・削除・再付与等を検査する。
このfixtureは実モデルの返答、実ユーザーの設定変更、クラウド転送のE2Eではない。

最終確認: host31スイート成功（既存28にcontext/index/品質評価を追加）。
Bitrig preview `2026-10-15T14-48-03-768e257e.log`成功、既存metadata警告1件。
Simulatorで起動後の既存WeeklySync/14:16のchat保持、空白Ask AIと既存Glassの
表示を確認。DEBUG自己チェックの失敗ログはなし。検索変更自体はhost fixtureでの
確認であり、実AIへ質問を送るSimulator E2Eは実行していない。

UI、Glass/FAB、履歴、実ソース、プラグイン/ツール権限、保存形式は変更しない。
派生索引を作り直すmigrationやユーザーデータの削除は不要。新規費用はない。
