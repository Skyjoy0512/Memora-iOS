# 性能監査 2026-11（保存・音声信号・Core ML）

対象は `a94efcc2` 以降の作業開始点。変更は `3b3d9687`（記録単位の保存）と
`f1d1f26b`（Accelerate と VAD の実行先）。測定はすべて Mac ホストで、
iPhone 実機の電池・熱・GPU/Neural Engine の稼働率は測っていない。
数値は同じ条件の連続実行の中央値で、信頼区間は出していない。

## 1. 保存: 全件 BLOB から記録単位へ

### 変更前

`memoraMeetings` は記録全体を 1 つの JSON 文書として持っていた。タイトルの
1 文字、タスクの完了、要約の到着のたびに、全記録を encode して BLOB を
書き直す。5 万件では 1 編集あたり 2.3 秒の encode と 300 MB の書込になる。

### 変更後

記録は `documents` 表の `memora.meeting.<id>` に 1 記録 1 文書で入り、順序は
`memora.meetings.archive.v1` の id 一覧が持つ。各文書は payload の SHA-256 と
payload そのもの。保存は変わった文書だけを encode して書き、順序が変わったとき
だけ id 一覧を書き直す。専用の表を作らないのは、`LocalStore` が記録モデルへ
依存すると、文書ストアだけを使う検査まで記録と要約の連鎖を抱えるため。

| 件数 | 全件 encode | 全件書込 | 1件編集（変更後） | 倍率 |
| ---: | ---: | ---: | ---: | ---: |
| 100 | 0.72 ms | 0.07 ms | 0.10 ms | 約 8 倍 |
| 1,000 | 7.5 ms | 0.54 ms | 0.65 ms | 約 12 倍 |
| 10,000 | 63.5 ms | 7.9 ms | 5.6 ms | 約 13 倍 |
| 50,000 | 325 ms | 39.8 ms | 27.8 ms | 約 13 倍 |

合成記録は 1 件約 620 バイト（要約・短文・転写なし）。実データは転写を含むため
1 件あたりが大きく、encode の差はさらに開く。1 編集の時間は記録全体との
比較（`Meeting` の等値比較）で決まるため件数に比例するが、係数は encode の
1/100 程度である。

### 読込

起動時は行を 1 回走査する。記録の復号は互いに独立なので、512 行ずつ集めて
最大 4 コアで復号し、manifest の順に戻す。同時に保持するのは 1 バッチ分だけ
なので、300 MB の BLOB を丸ごと持たない性質はそのまま。

| 件数 | 行（manifest + 走査 + 並列復号） | 旧 BLOB（読込 + 復号） | 差 |
| ---: | ---: | ---: | ---: |
| 100 | 1.17 ms | 0.80 ms | +0.37 ms |
| 1,000 | 4.9 ms | 7.1 ms | −30% |
| 10,000 | 55.6 ms | 74.4 ms | −25% |
| 50,000 | 258 ms | 378 ms | −32% |

100 件だけは固定費で 0.4 ms 遅い。1,000 件以上では BLOB より速い。
復号はスレッドをまたいで書き込むため、各スライスは重ならない範囲だけを
担当し、保存先は `UnsafeMutableBufferPointer` で渡している。

### 安全側の約束

- 切替は 1 トランザクション。行・manifest・旧 BLOB の退避が揃って確定する。
  切替の基準にした旧 BLOB が変わっていれば、そのトランザクションは確定しない。
- 切替時は旧 BLOB をオブジェクト境界で分割して保存するため、触っていない
  記録は元のバイト列のまま（未知のフィールドも残る）。
- 旧 BLOB は `memoraMeetings.legacy` に残す。行が壊れていた場合は読まずに
  旧 BLOB を読み、次の保存で作り直す。
- 行の digest は SHA-256。読込時に照合し、一致しない行は採用しない。

## 2. 音声信号

録音 tap は 512 サンプルだけを間引いて二乗和を取っていた。`vDSP_svesq` に
置き換え、全サンプルを測る。

| バッファ | 間引きループ | Accelerate |
| ---: | ---: | ---: |
| 512 | 227 ns | 18 ns |
| 4,096 | 159 ns | 131 ns |
| 8,192 | 200 ns | 252 ns |

録音 tap のバッファは 4,096 フレーム。8,192 では間引きの方が速いが、間引きは
8 サンプルに 1 つしか見ない。取り込んだ音声の信号検査（10 分のチャンクで
数千万サンプル）は、サンプルごとの Swift ループからベクトル演算へ変わり、
桁で速くなる。値は同じで、非有限値の検出も維持する。

## 3. Core ML（Silero VAD）

同梱モデルを実行先ごとに読み込み・推論した（3 回ずつ交互、中央値）。

| 実行先 | 読込 | 256 ms フレームの推論 |
| --- | ---: | ---: |
| `.all` | 15.4 ms | 0.156 ms |
| `.cpuAndNeuralEngine` | 14.8 ms | 0.157 ms |
| `.cpuAndGPU` | 0.65 ms | 0.156 ms |
| `.cpuOnly` | 0.61 ms | 0.158 ms |

推論は同じで、Neural Engine は 0.16 ms の推論に対して約 15 ms の準備を払う。
このモデルは CPU で走らせる。実機の消費電力・発熱・連続録音時の挙動は未計測。
出力は 4 つの実行先で 1e-3 以内に一致した。

## 4. 移行を起動後に回す（シミュレータ実測）

旧 BLOB からの切替は、これまで「最初の保存」の中で起動していた。5 万件では
その瞬間だけ画面が止まるため、起動直後に保存キューで移行するよう変えた。
iPhone 18 Pro Max シミュレータ（Debug ビルド）に合成 2,000 件（8.2 MB、転写12件/記録）を
置いて測った結果:

| 項目 | 時間 |
| --- | ---: |
| 起動（モデル準備完了まで、旧 BLOB 2,000 件） | 93〜108 ms |
| 起動（同じ 2,000 件を行から読む） | 100〜128 ms |
| 記録の移行（2,000 件、保存キュー上） | 2,044 ms |

移行はメインスレッドを使わない。切替後は
`memora.meeting.<id>` 2,000 件・manifest・`memoraMeetings.legacy`（8.2 MB）が残り、
旧 BLOB は消えていることを実コンテナで確認した。Debug ビルドの数値で、
Release や実機の比較ではない。

## 5. 未計測（この監査の境界）

- iPhone 実機の冷起動・MainActor 占有・フレーム落ち・RSS・電池・熱
- SwiftUI の body 再評価回数とスクロールのヒッチ
- 実データ（転写を含む記録）での移行時間とピークメモリ
- 実会議音声での日本語 CER、話者分離、VAD の削減率
- GPU の稼働率。Metal を使う変更はしていない
